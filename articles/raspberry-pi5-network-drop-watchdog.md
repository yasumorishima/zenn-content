## 症状

Raspberry Pi 5（Wi-Fi 運用、ヘッドレス）を SSH と Tailscale で常用しているのですが、ときどき **電源は入っている（LED は点灯）のに、ネットワークから完全に消える** ことがありました。

- LAN の SSH → timeout
- Tailscale の SSH → timeout
- RDP も timeout

しかも繰り返し起きて、毎回「電源を入れ直す」で復旧させていました。これを **原因の切り分け** と **自動復旧** までやったので残します。

## 切り分け1：`tailscale status` で「機器側か自分側か」を一発判別

SSH が通らないとき、つい「ラズパイが落ちた」と決めつけがちですが、**自分側（PC の Wi-Fi / VPN）が原因のこともある**ので、まずそこを切り分けます。

Tailscale を使っているなら `tailscale status` が一番速いです。

```text
100.x.y.z   raspberrypi   user@   linux   active; relay "..."; offline, last seen 1h ago, tx 124956 rx 0
```

ポイントは peer 行の **`offline, last seen 1h ago`**。これは Tailscale のコーディネーションサーバが持っている記録で、**自分の SSH とは独立した第三者の事実**です。

- peer が `offline` → 本当にラズパイ側がネットから落ちている
- peer が `active`/オンライン → 落ちているのは自分側（PC の VPN/ネット）

さらに `last seen` で **いつ落ちたか** も分かります。`tx ... rx 0` は「こちらからは送れているが相手から1バイトも返ってこない」状態です。

自分の PC 側も `tailscale status --json` の `BackendState=Running` / `Self.Online=true` で「自分は正常」を確認しておきます。

## 切り分け2：復旧後に `journalctl -b -1`（**前の** boot）を読む

ここが一番ハマりどころです。ネットから消えている間は当然ログを取りに行けません。復旧（再起動）してから読むことになりますが、**再起動した瞬間に「現在の boot」は新しくなる**ので、`journalctl`（デフォルト）や `dmesg` を見ても落ちた瞬間が入っていません。

落ちたときのログは **1つ前の boot** にあります。

```bash
# 直前の boot のログ全体（末尾）
journalctl -b -1 --no-pager | tail -30

# 落ちた当日の wlan0 / ネットワーク関連だけ
journalctl -b -1 --no-pager | grep -iE "wlan0|cfg80211|brcmfmac|LinkChange|network is unreachable" | tail -40
```

自分のケースで出ていたもの（時刻順）：

```text
19:57  avahi-daemon: Withdrawing address record ... on wlan0   # IPv6 アドレスが flap
20:08  tailscaled: LinkChange: major, rebinding ... rebind-reason=[time-jumped(13m50s),ips-changed,protocols-changed]
22:06  tailscaled: ... connect: network is unreachable          # 完全に不通
```

重要なのは、**この間もログは出続けていた**こと。つまり OS 全体のフリーズや OOM ではなく、**wlan0／ネットワーク層だけが落ちて不通になっていた**わけです（`journalctl -b -1` の末尾に `oom` も `panic` もなし）。

> 根本トリガー（なぜ wlan0 が落ちたか）まではログから特定しきれませんでした。ドライバの明示的な crash 行も出ておらず、`vcgencmd get_throttled` も復旧後は `0x0`（電圧低下フラグなし）。なので以降は「**wlan0 が落ちる事象一般への対症**」として watchdog を入れます。

## 対策：NetworkManager を再起動する watchdog

「OS は動いているのにネットだけ落ちる」なら、**cron で監視して、落ちていたらネットワークを再起動すれば自動復旧できる**はずです。Pi OS は最近 NetworkManager 運用（`resolv.conf` が `# Generated by NetworkManager`）なので、それを再起動します。

`/home/pi/.local/bin/net-watchdog.sh`：

```bash
#!/usr/bin/env bash
# gateway が不達なら NetworkManager を再起動して wlan0 を復旧させる
GATEWAY=192.168.1.1   # 自宅ルータのIPに置き換え
LOG=/home/pi/logs/net-watchdog.log
if ping -c 3 -W 3 "$GATEWAY" >/dev/null 2>&1; then
  exit 0
fi
echo "$(date -Is) gateway $GATEWAY unreachable, restarting NetworkManager" >> "$LOG"
systemctl restart NetworkManager
```

`/etc/cron.d/net-watchdog`（3分ごと、root 実行）：

```text
*/3 * * * * root /home/pi/.local/bin/net-watchdog.sh
```

インストール：

```bash
chmod +x /home/pi/.local/bin/net-watchdog.sh
mkdir -p /home/pi/logs
echo "*/3 * * * * root /home/pi/.local/bin/net-watchdog.sh" | sudo tee /etc/cron.d/net-watchdog
```

### 誤再起動しないことを確認

ネットが正常なときに余計な再起動をされると困るので、`ping` が通る状態で1回手で走らせて確認します。

```bash
/home/pi/.local/bin/net-watchdog.sh
echo $?        # → 0
cat /home/pi/logs/net-watchdog.log   # → ファイルなし（=再起動していない）
```

`ping` が通る間はログにも何も残らず、`systemctl restart` も走りません。落ちたときだけ動きます。

## まとめ

- 「電源 ON なのにネットから消える」は **ネットワーク層のドロップ**であることが多く、OS は生きている。
- 切り分けは **`tailscale status`（第三者の offline 記録）→ 復旧後に `journalctl -b -1`（前の boot）** の順が速い。
- 対症療法として **gateway を ping して落ちていたら NetworkManager を再起動する watchdog** を cron で入れておくと、OS が動いている限り数分で自動復旧する。
- ただし OS 自体が止まる系の障害には cron 駆動の watchdog は効かない点は理解しておく。

根本原因の特定はまだですが、少なくとも「毎回手で電源を入れ直す」運用からは抜けられました。

## 追記（続編）：gateway ping は通るのに外部だけ死ぬ「選択的な断」と watchdog v2

上の watchdog を入れてから約2週間後、今度は**まったく別のパターン**で死にました。しかも gateway への ping は通るので、上の watchdog は発火しません。

### 症状（前回と全く違う）

- SSH（Tailscale 経由）は普通に生きている
- gateway への ping も通る
- なのに名前解決が全滅（`getent hosts github.com` が失敗）
- 宛先によって挙動がバラバラ：
  - Google 系だけ HTTPS 200 が返る
  - GitHub / Cloudflare（1.1.1.1）/ その他 → TCP connect timeout
  - IPv6 は全滅

「Google だけ通る」ので ISP・ルーター障害に見えますが、結論から言うとこれも **Pi 自身（wlan0 の Wi-Fi クライアント状態の破損）** でした。

### 切り分け1：同じルーター配下の別端末から同じ宛先を叩く（これが決定打）

同じ Wi-Fi につながっている PC からは GitHub 等へ普通に繋がりました。→ **回線・ルーターは無罪、Pi 固有の問題**と確定。ここを省くと「ルーター再起動」という無駄な物理対応に進んでしまうところでした。

### 切り分け2：DNS サーバー単位の生死を UDP で直接確認

Pi に `dig` / `nslookup` が入っていなくても、python3 数行で DNS クエリを直接投げられます。

```python
import socket, struct

def q(server, timeout=3):
    # minimal DNS A query for github.com
    pkt = struct.pack('>HHHHHH', 0x1234, 0x0100, 1, 0, 0, 0)
    for part in b'github com'.split():
        pkt += bytes([len(part)]) + part
    pkt += b'\x00' + struct.pack('>HH', 1, 1)
    s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    s.settimeout(timeout)
    try:
        s.sendto(pkt, (server, 53))
        data, _ = s.recvfrom(512)
        return f'OK answers={struct.unpack(">H", data[6:8])[0]}'
    except Exception as e:
        return f'FAIL {type(e).__name__}'
    finally:
        s.close()

for srv in ['192.168.1.1', '100.100.100.100', '8.8.8.8', '1.1.1.1']:
    print(srv, '->', q(srv))
```

結果は `ルーター=FAIL / Tailscale MagicDNS=FAIL / 8.8.8.8=OK / 1.1.1.1=FAIL`。つまり「DNS が死んでいる」のではなく「**特定宛先への通信そのものが死んでいる**」ことが分かります（DNS 失敗はその一症状にすぎない）。`ip route get` も UFW も正常でした。

### 復旧：wlan0 の完全再接続（`reapply` では直らない）

`nmcli dev reapply wlan0`（設定の再適用）では直りませんでした。**disconnect → connect の完全再接続**が必要です。SSH 自体が wlan0 越しなので、途中で切断されても最後まで走るよう detach して実行します。

```bash
sudo nohup bash -c 'nmcli dev disconnect wlan0; sleep 3; nmcli dev connect wlan0' >/dev/null 2>&1 &
```

約20秒で復帰し、全宛先が 200 に戻り、**最初「死んでいる」ように見えたルーター DNS も復活**しました。つまり DNS 死・選択的 timeout・IPv6 全滅は、すべて wlan0 の状態破損という単一原因の症状でした。

### watchdog v2：外部疎通も監視する

gateway ping だけでは今回のパターンを見逃すので、tier2 を追加した v2 に更新しました。

```bash
#!/bin/bash
# net-watchdog v2: two-tier self-healing
# tier1: gateway unreachable -> restart NetworkManager
# tier2: gateway OK but external connectivity mostly dead (<2 of 4 probes) -> full wlan0 reconnect
LOG=/home/pi/logs/net-watchdog.log
STATE=/home/pi/logs/net-watchdog.last-reconnect
GW=192.168.1.1   # 自宅ルータのIPに置き換え
mkdir -p /home/pi/logs

if ! ping -c3 -W3 $GW >/dev/null 2>&1; then
  echo "$(date -Is) gateway unreachable -> restart NetworkManager" >> $LOG
  systemctl restart NetworkManager
  exit 0
fi

alive=0
for url in https://www.google.com https://github.com https://1.1.1.1 https://www.yahoo.co.jp; do
  curl -4 -sS --max-time 5 -o /dev/null "$url" 2>/dev/null && alive=$((alive+1))
done

if [ "$alive" -lt 2 ]; then
  now=$(date +%s)
  last=$(cat "$STATE" 2>/dev/null || echo 0)
  if [ $((now - last)) -lt 1800 ]; then
    echo "$(date -Is) external dead (alive=$alive/4) but reconnected <30min ago, skip" >> $LOG
    exit 0
  fi
  echo "$now" > "$STATE"
  echo "$(date -Is) gateway OK but external dead (alive=$alive/4) -> wlan0 reconnect" >> $LOG
  nmcli dev disconnect wlan0
  sleep 3
  nmcli dev connect wlan0
fi
exit 0
```

設計のポイント：

- 4つの独立した宛先のうち **2つ以上生きていれば正常扱い**（1サイトの障害だけでは誤発火しない）
- `https://1.1.1.1` は IP 直打ちなので **DNS が死んでいても機能する probe**
- 再接続は **30分クールダウン**付き（フラッピング防止）
- 正常時に手で実行して「何もしない」ことを確認してから cron に載せる（v1 と同じ）

### 続編の教訓

- gateway ping 監視だけでは「Wi-Fi クライアント状態の破損による選択的な断」を見逃す
- 「一部のサイトだけ通る」は ISP 障害に見えて、**機器側の可能性がある**。同一 LAN の別端末から同じ宛先を叩く cross-check が最速の切り分け
- `nmcli dev reapply` と「完全再接続（disconnect/connect）」は別物。直らないときは完全再接続まで落とす
