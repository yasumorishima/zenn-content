M5Stack の公式スタックちゃん（M5STACK-K151、頭脳は CoreS3）で、**電池残量の表示が 0% から動かない**という症状に一週間ほど付き合いました。

結論から書くと、**直りましたが、直った理由が分かりません**。

それでも調べる過程で分かったことは同じ症状の人の役に立ちそうなので、**何を確かめて、何を除外したか**をそのまま残します。「これをやれば直る」という記事ではありません。

## 症状

- 起動直後から電池残量の表示が **0%** のまま
- ベース側のポートでも本体側のポートでも変わらない
- スマートフォン用の充電器で一晩つないでも 0%
- ケーブルを抜くと即座に電源が落ちる時期があった（後日、即断はしなくなった）

## まず確かめた「正常な挙動」

### 表示はレジスタ 1 本を読んでいるだけ

残量表示は AXP2101 の残量計レジスタ（0xA4）を読んだ値をそのまま出しています。凝った推定はしていないので、**表示が 0% なら残量計そのものが 0 を返している**ということです。

残量計は電源投入時に有効なので、「有効化を忘れている」という線は最初に消えました。

### ファームは起動のたびに充電電流を 700mA に設定する

ここが一番の収穫でした。M5Stack のファームウェアは公開されていて、電源まわりの初期化にこう書かれています。

```cpp
Pmic(i2c_master_bus_handle_t i2c_bus, uint8_t addr) : Axp2101(i2c_bus, addr)
{
    // ... 省略 ...
    auto ret = setChargerConstantCurr(XPOWERS_AXP2101_CHG_CUR_700MA);
    if (!ret) {
        ESP_LOGE(TAG, "Set charge current failed");
    }
}
```

このコンストラクタはボード初期化から呼ばれるので、**起動のたびに必ず 700mA が設定されます**。

つまり **PC の USB ポート（一般に 500mA）では、そもそも設定値に足りません**。「PC につないでも充電されない」のは故障ではなく仕様どおりの挙動でした。ここを故障と誤解しやすいので、切り分けの最初に潰しておく価値があります。

### 自作ファームでは残量計をリセットできない

「自分でビルドして残量計を初期化すればいい」と考えましたが、これは行き止まりでした。公開されているソースのうち、コンパニオンアプリとの認証に関わる部分が**スタブ**（固定文字列を返す弱いシンボルで、公式ビルド時に本物が差し込まれる）になっており、自作ファームを書くとアプリとのペアリングが通らなくなります。**公式バイナリを使う前提**から動けません。

### CoreS3 の電源管理チップには既知の厄介事がある

CoreS3 の AXP2101 は、I2C の波形がぎりぎりでレジスタ値がランダム化する事例が報告されています。厄介なのは **再書き込みでは戻らず、電源の完全な遮断だけが復旧手段**という点です。この時点で「放電しきってから満充電する」を次の一手に据えました。

## やっていないこと（重要）

原因を語る前に、**自分が何をしていないか**をはっきりさせておきます。

- 電源管理チップのレジスタには **一度も書き込んでいません**
- 残量計のリセットも **していません**
- 本体に対して行った書き込みは、設定領域（NVS）への 1 エントリ追記だけです

これを言葉ではなく実測で示すために、**設定領域を書き込み前と後でダンプして差分**を取りました。

```
書き込み前のキー数: 18   現在: 20
--- 増えた ---
  + wifi/ota_url          ← 自分で追記したもの
  + warm_boot/app_index   ← ファームが自分で書くもの
--- 消えた ---
  （なし）
--- 中身が変わった ---
  * phy/cal_data          ← Wi-Fi の校正値、ファームが自分で書くもの
```

電池にも電源にも関係するキーは動いていません。

## そして直った

ある朝、**表示が 100% になっていました**。何をしたから、が分かりません。

一つだけ、筋の通る仮説はあります。**未検証**として書きます。

前日、設定領域を読み書きするために `esptool` を何度も実行し、シリアルも繰り返し開いていました。`esptool` を使っている間、本体は**ブートローダにいてファームウェアが動きません**。

ということは、**あの「起動のたびに 700mA」の設定が一度も行われないまま、USB から給電され続けていた**ことになります。この状態なら電源管理チップは電源投入時の既定値のままなので、PC のポートでも充電が進みうる、という筋書きです。

「PC につないだまま長時間ブートローダに置く」ことをしたのは、その日が初めてでした。

しかも**その日は一日中 USB につないだまま**でした。それまでは作業のたびに抜き差ししていたので、「長時間つなぎっぱなし」と「長時間ブートローダにいた」が同時に起きたのは、この日だけです。どちらが効いたのか、あるいは両方なのかは分けられていません。

ただし**チップ側の既定充電電流の実値を確認していない**ので、仮説の域を出ません。確かめるなら、動作中に該当レジスタを読んで既定値と突き合わせる必要があります。

## 副産物として分かったこと

本題ではありませんが、同じ機体を触る人には効くはずの事実です。

### 待機中に首を振るのは設定で止められる

「話しかけていないのに 4〜8 秒ごとに首を振る」動作は、**本体の設定で消せます**。

```
SETUP → AI.Agent → General → Idle movement frequency: を Off → Confirm
```

段階は Off / Low / Medium / High の 4 つで、**既定は Medium**。Off にすると待機動作の仕組み自体が登録されなくなります。

「無効化する手段がない」と書かれた Issue が残っていますが、それは起票時点の話で、その後の版で設定が入っています。**古い Issue の記述を現在の仕様と思い込まない**、という教訓込みで書いておきます。

### アイドルで勝手に電源が落ちる

放置していると自動的に電源が落ちます（`SETUP → AI.Agent → Power Saving`）。実測では、ランチャーに戻したまま **12 分ほどでシリアル出力が止まり、ping も通らなくなりました**。

「電源が入っているつもりで作業していたら、実はとっくに落ちていた」ということが起きます。切り分けの最中は、頼む前に生きているか確認したほうが早いです。

### ランチャーか AI エージェントかは空きメモリで見分けられる

シリアルログに 10 秒ごとに出る空き SRAM の値で判別できます。

| 状態 | 空き SRAM |
| --- | --- |
| ランチャー | 約 146k |
| AI エージェント稼働中 | 約 38k |

心拍ログ自体はどちらの状態でも出るので、**行の有無では判定できません**。値を見る必要があります。

### 設定領域を読むときの落とし穴

ダンプを自分で解析する場合、次の 2 点でつまずきました。

**エントリの状態ビットは `0b10` が有効**です（`0b11` が未使用、`0b00` が消去済み）。ここを取り違えると、33 個あるエントリのうち数個しか見えません。

**CRC の流儀は実機のエントリで較正するのが確実**です。候補を総当たりしたところ、ファームが書いた既存エントリ 33 件すべてに一致したのは 1 つだけでした。

```
# 33/33 一致した流儀
binascii.crc32(buf, 0xFFFFFFFF)

# 一致しなかったもの
binascii.crc32(buf, 0)
binascii.crc32(buf, 0) ^ 0xFFFFFFFF
binascii.crc32(buf, 0xFFFFFFFF) ^ 0xFFFFFFFF
```

項目そのものの CRC と、文字列データの CRC の両方に同じ流儀を使います。仕様書から導くより、**実機が書いた値に合わせるほうが早くて確実**でした。

なお設定領域のダンプには Wi-Fi の資格情報が平文で入ります。解析スクリプトは**キー名だけを出して値は出さない**作りにしておくと事故が減ります。

## まとめ

- 表示が 0% から動かない症状は直りましたが、**直った理由は分かりません**
- **PC の USB で充電されないのは故障ではありません**。ファームが起動のたびに 700mA を要求するためです
- 電源管理チップのレジスタ異常は**電源の完全遮断だけが復旧手段**という既知の事例があります
- 自作ファームで直そうとしても、認証部分がスタブなので**公式バイナリから離れられません**

同じ症状に当たった方が、少なくとも「これは故障ではない」と切り分けられる材料になれば十分です。
